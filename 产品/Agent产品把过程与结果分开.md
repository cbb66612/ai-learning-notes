# Agent产品把过程与结果分开

普通表单提交后，用户通常能直接看到保存结果。Agent 任务可能经过规划、检索、工具调用和文件生成，界面上的“完成”就变得复杂了。我想弄清的是：产品如何既让人看懂它在做什么，又不把中间一步的成功包装成整个目标已经达成。

## 从用户要的结果定义完成

判断完成应从任务终点倒推。用户要一份可下载的表格，终点包含文件存在、能够打开、字段符合约定；用户要查询订单，终点是找到了对应记录并给出准确状态。工具返回一个成功码，只说明某次调用满足了工具自己的约定，未必覆盖这些要求。

因此，任务可以区分准备中、执行中、等待确认、已生成、检查未通过等状态。状态不是越多越好，而是让用户能决定下一步。对使用者无意义的内部步骤可以收起，影响等待、费用、权限或结果可靠性的变化则应清楚显示。

“已提交”与“已完成”尤其需要分开。外部系统接收任务后可能继续排队，网络中断也可能使界面暂时不知道最终状态。此时给出“正在查询执行结果”比直接宣布失败或成功更准确，也能减少用户重复点击造成的重复操作。

## 展示有用的过程信息

过程展示的价值在于解释进度、提供控制和帮助恢复。我更愿意显示正在查询哪类资料、使用了什么工具、是否需要用户补充信息，以及已产生哪些可用结果。无需把模型所有内部推理铺在页面上，冗长文字并不等于透明。

耗时较长的任务应允许取消或离开后回来查看。取消还要说明边界：尚未执行的步骤可以停止，已经写入外部系统的动作可能无法自动撤回。对有实际影响的操作，确认界面应展示对象和内容，用户批准的范围应与后续执行一致。

失败提示也要对应恢复动作。资料不足时可补充输入，权限不足时可联系相应负责人，服务暂时不可用时可稍后重试。把所有失败都归为“请重新生成”，会让用户反复支付时间，却不知道哪一部分需要改变。

## 假设例子：整理资料清单

假设用户上传若干文档，希望 Agent 提取标题、作者和主题，生成可编辑清单。页面可以先显示哪些文件已读取，再显示哪些文件无法解析；生成表格后给出缺失字段提示，并允许回到原文核对。这样用户能接受部分完成，也能知道剩余工作在哪里。

如果系统只成功创建了一个空文件，不应显示“资料整理完成”。如果只读取了部分文档，也不能悄悄把结果当成全量清单。更合适的是标出已处理范围、未处理原因和继续处理入口。这里的检查不必追求完全自动化，关键是把不能确认的内容呈现出来。

假如后来更换模型，不能只比较两次是否出现了“完成”提示。还应使用相同任务和资料，检查漏项、字段错误、等待体验与人工修改量。若同时修改了提示词、工具和资料，观察到的变化只能归于整体方案，无法仅凭页面结果确定是模型带来的改善。

## 对交互设计的理解

Agent 的不确定性不应全部转交给用户，但也不能藏起来。好的界面需要提供默认路径、明确状态和必要的检查点，让用户在合适的时候介入。频繁弹窗会打断任务，毫无确认又可能越过用户意图，两者之间要根据操作影响和可恢复程度取舍。

我会练习画一张状态图，再给每个状态写一句用户能理解的话，配上一个真正有用的操作。随后用工具失败、结果为空、部分成功和重复提交走一遍。如果用户只看页面就能判断是否完成、哪里没完成以及怎样继续，过程与结果才算在体验上分开了。

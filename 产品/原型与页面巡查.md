# 原型与页面巡查

我把产品检查分成两个时点：开始写代码前检查流程，做出页面后检查真实使用。它们回答不同的问题。

## 开发前：低保真走完整条路

把入口、主要操作、结果、失败恢复排在一张流程图或低保真长页里。每一屏写清：

- 这个页面属于哪一步；
- 用户能做什么，下一步到哪里；
- 首次使用、加载、空数据、无权限、失败时显示什么。

这一步只关心信息和流程。材料没说明的功能标成“待确认”，不为了让原型完整而擅自补需求。

## 开发后：沿真实路径巡查

打开实际运行的产品，按用户顺序走一遍。每个问题记录页面、状态、操作路径和具体反馈；下一轮保留原意见，对改过的地方回查。一个简单的标记就够用：**可用 / 待改 / 阻塞**。

我的检查表：

1. 入口和主路径能否到达结果？
2. 空、加载、失败和恢复状态是否可理解？
3. 操作后的反馈是否准确？
4. 页面文案和按钮是否与实际功能一致？
5. 上一轮反馈是否真的关闭？

低保真图不能证明可用性；截图也不能替代点击、接口、权限和性能检查。实际没有走到的分支，先记“未检查”。

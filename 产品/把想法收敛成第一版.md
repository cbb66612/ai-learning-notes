# 把想法收敛成第一版

一个想法越早变成功能列表，越容易绕过“到底要解决谁的什么问题”。我现在习惯先写一页概念卡，再谈页面和技术。

## 先问三个视角

1. **使用者**：谁会在什么场景遇到问题？目前怎么解决？频率如何？
2. **持续方式**：这个产品要验证什么？谁维护数据和服务？成本从哪里来？
3. **实现约束**：做成网页、App 还是工具？需要账号、外部接口或特殊权限吗？

三个视角不必一次答完。知道与不知道的部分要分开写，避免把假设当成结论。

## 概念卡的最小内容

| 问题 | 当前回答 |
| --- | --- |
| 目标用户和使用场景 | 用一句具体的话描述 |
| 现有替代方法 | 用户今天是怎么做的 |
| 第一版只解决的事 | 一个核心任务，能走到结果 |
| 成功信号 | 可以观察到的行为或结果 |
| 依赖与未知项 | 数据、权限、成本、技术限制 |

当这些回答能够相互对上，才把范围写成“本版必须有、暂不做、待确认”。新想法仍可进入，但每次都要说明它对流程和交付时间的影响。

## 容易踩的坑

- 口头说“会用”不等于真实使用；还要看当前替代方法和使用频率。
- MVP 不是尽量少的页面，而是最短的完整任务路径，包含失败与恢复。
- 范围冻结不是永远不改，而是让变更有记录和判断依据。

**接下来想验证**：拿一个实际项目，用概念卡和直接列功能两种方式分别讨论，看哪一种更快暴露关键未知项。

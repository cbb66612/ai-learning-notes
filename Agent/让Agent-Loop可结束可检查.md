# 让 Agent Loop 可结束可检查

## 把完成条件放在循环之前

我理解循环的意义，是让系统根据环境反馈修正行动，而不是不断生成下一条计划。开始设计时，先把用户目标改写成可检查的结果。例如“整理资料”过于宽泛，可以进一步明确要处理哪些文件、怎样分类、产物存在哪里、哪些原始内容不能改。目标说不清，停止判断也会跟着摇摆。

完成检查要与任务匹配。生成文件时可以核对文件是否存在、格式能否解析、必要内容是否齐全；修改程序时可以运行相关检查；处理业务记录时要读取真正的结果状态。模型说“已经完成”可以触发检查，却不能替代检查。反过来，程序退出码正常也只说明该程序按自己的规则结束，不必然证明用户目标已经满足。

## 给循环几种明确的出口

我会区分正常完成、等待信息、预算耗尽和执行失败。它们应当有不同的状态与交接内容。正常完成交付结果；等待信息说明缺少什么；预算耗尽保存进度和未完成项；执行失败留下能定位问题的记录。把所有出口都写成“完成”，会让后续用户与程序误解状态。

预算也不只是最大轮数。一次调用可能长时间无响应，少量步骤也可能触发昂贵服务，因此可以分别限制总时间、调用次数和任务允许的资源。限制值要依据任务和实际测量设置，没有通用的最佳数字。达到上限应当停在可解释的位置，而不是换一个子任务继续消耗同一份预算。

## 检查进展，而不只计算步数

重复调用同一个工具不一定是错误，分页读取就需要重复。真正值得警惕的是输入、结果和任务状态没有发生有意义的变化。可以记录本轮新获得的事实、完成的子目标、尚未解决的问题。如果多轮只改写计划而没有新观察，应考虑更换调查方向、请求信息或结束尝试。

一个假设例子是资料检索助手连续搜索同一问题。第一次没有找到结果，第二次改用同义词有合理依据；如果后续只是把词序换来换去，且候选资料完全相同，就不应无限继续。停止理由可以是当前数据范围不足，而不是断言世界上没有答案。这样的区分也能防止把检索失败误写成事实结论。

## 恢复要看错误性质

网络暂时超时、参数格式错误、权限不足、资源已删除，需要不同处理。暂时错误可以有限重试；参数错误应修正输入；权限不足不能靠重复尝试绕过；资源变化需要重新确认任务条件。重试之前还要确定上一次写操作是否已经成功，避免因为响应丢失而重复创建或发送。

检查点应保存目标、已确认状态、产物位置和下一步，不必把全部聊天原封不动复制。恢复时先读取外部真实状态，再决定从哪里继续。对于已经影响外部系统的步骤，要说明哪些能撤回、哪些只能补偿，以及哪些需要用户接手处理。检查点是恢复线索，不是现实状态永远不变的保证。

## 一次练习怎样判断有效

我会用同一个小任务构造正常完成、工具超时、返回空结果和中途取消几种路径。检查的不只是最后一段回答，还包括任务是否停止、产物是否完整、重复执行是否产生副作用、保存状态能否支撑继续工作。

运行记录需要能串起任务与步骤，但不应无差别保存敏感原文。保留必要的输入摘要、工具状态和检查结果，通常比堆积大量日志更容易诊断。一个清楚的循环，应该让人看出它为什么继续、为什么停止，以及结束时究竟完成了多少。

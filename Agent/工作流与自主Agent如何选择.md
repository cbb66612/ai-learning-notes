# 工作流与自主 Agent 如何选择

## 先看任务怎样变化

我不把自主程度当成系统先进程度。选择形态时，更有用的问题是：任务步骤能否提前说清，途中得到的信息会不会改变下一步，以及错误动作的代价有多大。只有这些条件明确了，才有理由讨论使用单次模型调用、固定工作流或动态 Agent 循环。

单次调用适合输入与输出边界清楚的任务，例如把一段反馈分类。工作流把节点和转移规则写在程序里，模型可以负责某个节点的理解或生成。动态 Agent 则根据观察选择后续动作。三者可以组合，真实系统不必给自己贴一个唯一标签。

## 固定工作流提供什么

工作流的优势是路径可见。每个节点输入什么、产生什么、失败后去哪里，都可以单独检查。对于资料审核、表单处理或标准问答，稳定步骤让权限、重试和状态恢复更容易安排。模型输出仍可能不稳定，但系统可以用结构校验与业务规则约束它。

工作流也会付出维护成本。分支很多、环境经常变化时，图可能越来越复杂。这里要区分“业务确实需要动态探索”和“流程尚未分析清楚”：不能因为当前画不出流程，就立即把规划责任全部交给模型。先观察真实任务，往往能发现大部分路径其实相当稳定。

## 动态循环增加了哪些能力与负担

动态 Agent 适合下一步依赖新发现的场景。假设要排查一份公开数据为什么不一致，可能先读说明，再检查字段，再查另一份资料；这些动作的顺序未必能完全预设。只读探索允许系统根据中间结果调整方向。

与此同时，动态循环需要承担更多控制工作：如何判断没有进展，何时停止搜索，预算如何分配，工具失败后能否恢复。长路径可能带来更高延迟与费用，但具体大小必须实际测量，不能用通用倍数代替。自主选择也不自动意味着覆盖长尾更好，错误计划同样可能把任务带偏。

## 一个混合方案的假设例子

假设要做一个资料整理助手。固定流程先确认输入、检查访问权限、建立任务记录；在“补充资料”节点内允许一个有步数上限的探索循环；之后回到固定流程生成摘要、检查引用并交给用户审阅。这样，动态能力只出现在真正需要它的地方。

如果任务后来增加对外发布，发布动作仍由明确节点负责，不能因为前面允许探索，就连带允许任意外部写入。能力范围应按动作与场景定义，而不是笼统地给整个 Agent 一个“全自动”开关。

还有一种常见情况是流程总体稳定，只有少数输入无法自动处理。此时可以把这些输入送入明确的异常分支，先收集它们的共同特征，再决定是否值得引入动态规划。异常数量少、处理规则又容易说明时，人工接管或补一个规则可能更合适。评估复杂度要同时考虑后续维护、排错和交接，而不只看第一次演示的代码量。

## 我会怎样做选择实验

首先用最简单方案跑一组具有代表性的任务，记录它不能处理的部分。若失败主要来自分类不准，应先改输入或模型；若失败来自确实无法预设的步骤，再尝试小范围动态循环。比较时保持任务、工具和验收标准一致，分别看完成情况、人工接管、成本和错误类型。

一个可用的决策记录应写明：为何选择当前形态，放弃了什么，什么条件出现时需要重评。比如工具范围扩大、任务由只读变成写入、用户要求更稳定的响应时间，都可能改变判断。选择架构不是一次永久承诺，而是根据实际任务持续收敛的过程。

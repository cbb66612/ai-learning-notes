# 上下文窗口怎样分配

## 容量问题与使用问题分开看

上下文窗口限制了模型一次处理信息的范围，通常以 token 计量。它不是汉字数或字符数，具体文本要用相应的计数方式估算。不同模型对输入、输出和内部处理的限制可能不同，实施时需要核对所用服务的定义，不能把宣传中的窗口大小直接当成可塞入资料的空间。

即使没有超限，信息过多也可能增加查找难度。重要约束被重复历史包围，过期资料与当前事实冲突，都会影响回答。因此我把两个问题分开：一是请求能否被接受，二是当前步骤能否获得清楚、相关、足够的信息。更长的窗口提供容量，并不自动完成信息整理。

## 按用途盘点信息

我会把上下文拆为稳定规则、当前请求、必要工具说明、检索材料、历史状态和输出空间。先确认哪些内容是本轮必须使用的，再决定哪些可以按需读取。预算没有通用比例，短问答和长调查的需求明显不同，固定比例反而容易把关键材料挤掉。

工具也不是越多越方便。无关工具描述会占用空间，并增加选择干扰。可以根据任务提供一组必要工具，再保留获取更多能力的途径。检索材料则应保留文档标识、时间或版本等解释所需的元信息。只有正文而没有上下文，可能使正确片段被用到错误对象上。

## 一个容易算错的例子

假设十二次工具调用各返回两千 token，原始返回合计是两万四千 token，单凭这些内容并不会填满一个十二万八千 token 的窗口。是否超限，还要加上规则、用户输入、既有历史、工具定义和输出等占用。更复杂的计费或重复发送问题也需要另算，不能把总调用量直接当成某一次请求的长度。

这个例子提醒我，遇到窗口问题应先查看每次请求的真实组成。若只是某个工具一次返回整份长文，可以改成摘要加定位信息，再按需获取原文片段；若是历史不断累积，就应整理状态；若当前任务本身太大，可能需要按子任务分阶段处理。不同成因不应统一用粗暴截断解决。

## 摘要与外置资料怎样配合

摘要适合压缩叙述，不适合随意改写决定结果的字段。编号、金额、日期、否定条件和未解决问题需要明确保留。摘要还应区分事实、推测与待办，避免把“准备检查”压成“已经检查”。重要原文保留可访问的位置，后续有疑问时能够回看。

外置状态负责记录任务进展，检索负责挑选资料，两者并不相同。当前订单状态应从业务系统查询，而不是从旧对话猜测。历史偏好可以帮助表达，但遇到新的用户指令要重新判断是否适用。权限结论同样可能过期，不能作为永久有效的文字缓存。

## 用任务效果检验整理策略

我会先选择一个有明确结果的小任务，记录原始输入长度、完成情况和关键事实遗漏，再逐项尝试减少重复、改用摘要或按需读取。每次只改变有限因素，才能看出效果来自哪里。减少 token 只是一个结果，还要观察是否增加额外检索、是否丢失条件、总耗时是否反而变长。

最后检查边界情况：长资料中间的例外规则是否仍能找到，用户刚改过的要求是否被旧摘要覆盖，工具失败信息是否被遗漏。上下文管理的目标是让系统在恰当时刻看到恰当内容，而不是单纯把输入压到最短。

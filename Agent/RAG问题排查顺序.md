# RAG 问题排查顺序

## 从一条具体失败问题开始

RAG 在回答时引入外部检索材料，但资料进入上下文并不保证答案正确。遇到答错，我会先保存一条完整案例：用户问了什么，理想答案需要哪些事实，实际返回了什么，以及当时使用的资料版本。没有具体案例，讨论容易变成换模型、改提示词或加大检索数量的反复尝试。

排查顺序可以沿着资料、检索、上下文和生成逐层向后看。每层都留下输入与输出，才能知道错误第一次出现在哪里。同一条问题可能有多个原因，例如资料解析漏了一行，同时生成阶段又没有识别证据不足，因此定位后也需要继续检查后续环节。

## 资料是否存在且能够被正确理解

先在原始资料中找到应当支持答案的内容。如果资料根本没有答案，检索算法无法凭空补全；如果文档过期，系统可能忠实复述错误信息。还要确认问题适用的对象、地区和时间范围，避免用名称相近但条件不同的规则作标准。

接着检查解析和切分。表格的行列关系、标题层级、脚注与例外条款都可能在转成文本时丢失。切块太短会拆开条件与结论，太长会把多个主题混在一起。选择策略时应看文档结构与失败案例，而不是相信固定长度对所有资料都最优。

## 正确内容有没有进入候选结果

如果资料与解析正常，再检查查询如何变化。改写可能补充同义表达，也可能擅自改变用户意图；路由和过滤可能缩小范围，也可能误排除必要文档。编号、产品名和专业词有时需要精确匹配，语义相近并不代表指向同一对象。

我会查看候选列表中是否出现相关片段，以及它们为什么没有进入最终结果。若召回阶段就缺失，优先检查索引更新、过滤条件、查询表达和检索方式；若候选中有而重排后消失，再观察排序依据。增加候选数量可能改善覆盖，也可能引入噪声，需要用同组问题比较。

## 模型实际看到了哪些内容

检索到正确资料后，还要检查上下文组装。截断、去重和摘要都可能丢失关键限制。引用编号应当稳定地对应片段，不能因为重新排序而错连。多个版本冲突时，需要依据适用范围判断，而不是简单选最长、出现最多或日期最新的一条。

假设问题问的是某类服务的退订条件，正确段落写着通常规则，紧接的例外条款却被截走。模型可能给出表面有引用、实际不完整的答案。这种失败应优先修复资料组合与条件保留，不能仅通过要求模型“更加严谨”解决。

还要注意缓存可能掩盖改动效果。检索或资料更新后，如果请求仍命中旧答案，表面上像是修改无效。诊断时应记录是否使用缓存、缓存对应的资料版本，以及它是否满足当前权限和时效条件。确认这些条件后，再判断新的检索策略究竟发生了什么变化。

## 最后检查回答与支持关系

生成阶段需要检查是否回答了用户真正的问题，是否添加上下文没有支持的内容，以及引用能否支持紧邻的结论。答案可能在现实中恰好正确，却来自模型原有知识；对于要求依据资料回答的任务，这仍不能证明检索链路有效。

我会把同一案例分别做两次诊断：一次保留实际检索结果，一次提供人工确认的必要资料。如果后者仍失败，更应关注生成、任务理解或判断标准；如果后者成功而前者失败，再追查检索和组装。每次修改后加入相似问题、不可答问题与例外条件，避免只修好一个措辞。这样积累下来的，是能定位原因的问题集，而不是一串偶然成功的演示。

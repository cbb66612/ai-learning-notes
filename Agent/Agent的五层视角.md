# Agent 的五层视角

## 用五个问题拆开一个系统

学习 Agent 时，我容易被模型、工具、记忆和框架名称混在一起的描述绕晕。现在更愿意用五个问题来拆解：它要完成什么，当前知道什么，能够做什么，运行由谁管理，以及怎样根据结果继续。这是我整理职责的方式，并不是唯一的标准架构。

同一个应用可以把这些职责写在很少的代码里，也可以拆成多个服务。重点不是组件数量，而是出错时能否找到责任位置。如果目标模糊、资料过期或工具权限错误，单纯换模型未必解决问题。按职责观察，能让讨论从“智能不够”变成具体的改进事项。

## 第一层是目标与计划

目标规定结果，计划提出达到结果的路径，两者不应混为一谈。用户要一份能使用的资料目录，系统可能选择扫描、分类、去重和生成导航；如果某一步发现资料不足，可以调整路径，但不能偷偷改变用户希望得到的结果。

我会先写清范围、约束与完成条件。计划适合拆成可以观察进展的小步，避免一次写出很长但从不更新的清单。对于信息不足的任务，计划中也可以包含调查和澄清步骤。它不必预知所有变化，却需要知道哪些变化会影响原目标。

## 第二层是上下文，第三层是行动

上下文是当前决定所需的信息，包括用户要求、相关资料、工具能力和任务状态。全部历史并不等于有效上下文：旧信息可能干扰新要求，重复内容可能掩盖例外。整理上下文时，要让事实有适用范围，让未确认的判断仍然保持未确认。

行动则把决定转化为可观察的变化。工具可以查询资料、执行计算、生成文件或操作业务对象。模型提出调用意图后，参数检查、身份权限与实际执行仍由程序处理。工具返回的错误和结果会成为下一步的观察，因此接口质量直接影响循环能否纠偏。

## 第四层是运行支撑

运行支撑负责让任务有状态、有边界、能恢复。例如保存检查点、限制资源、处理取消、隔离执行环境、记录必要日志，并在关键动作前等待用户判断。它经常被统称为运行框架，但具体需要哪些能力，应由任务风险和复杂度决定。

我特别关注完成检查放在哪里。若产物是程序，相关测试能提供一部分反馈；若产物是文章，还需要检查内容是否满足要求。任何检查都有覆盖范围，不能把格式正确等同于任务成功。运行支撑要把检查结果反馈给决策，同时避免让模型自报成功就直接结束。

这种拆分还适合定位接口问题。假设工具返回结果没有说明是否完整，上下文层可能把部分结果当成全部，循环层便提前结束。修复可以从工具返回协议入手，同时在完成检查中核对数量。问题虽然跨越几层，却不一定需要新增服务；先把职责和信息传递说清，往往比增加框架更有效。

## 第五层是循环与反馈

循环把前面几层串起来：读取状态，决定行动，接收结果，更新判断，然后完成、继续或交接。循环次数更多不意味着理解更深。工具持续报错、信息没有增加、预算已耗尽时，应进入相应出口，而不是不断生成近似计划。

可以用一个假设任务练习这五层：为一组公开文章生成主题索引。目标层规定范围与产物；上下文层提供当前文章和分类规则；行动层负责读取与写入；运行支撑保存进度并限制目录；循环层检查分类缺漏后决定继续还是结束。这样画一遍，就能看出缺失能力究竟位于哪里，也能判断一个简单脚本是否已经足够。

# ReAct 循环的观察与停止

## 理解推理与行动怎样交替

ReAct 让我注意到一个重要区别：模型可以在生成答案前与环境交互，并根据得到的观察调整后续行动。原始研究把推理文本、动作和环境反馈交替组织，让任务处理不只依赖一次静态输入。它是一种组织方式，并不等同于完整的业务系统架构。[ReAct 研究项目](https://react-lm.github.io/)

学习这种机制时，我更关注可观察的任务状态，而不是把长篇自我解释当作可靠性证明。一个理由写得合理，实际调用仍可能使用错误对象；一个最终回答很自信，外部动作仍可能没有成功。工程记录可以保留简要决策说明、工具输入输出和状态变化，无须把内部推理全文作为必需接口。

## 观察必须来自实际执行

模型提出工具调用后，运行程序真正执行，并把结果返回给模型。这个返回结果才是下一轮可以利用的观察。若模型自己写出“查询成功，库存充足”，而没有实际调用或可靠数据支持，那只是生成文本，不能与环境反馈混同。

工具错误也属于观察的一部分。超时、对象不存在、参数错误和没有权限，应提供足够清楚的状态，帮助系统决定重试、修正、澄清或停止。把这些情况全部转成空字符串，会让模型无法分辨没有结果和系统故障，也容易在缺少依据时自行补出答案。

## 用一个假设任务走一圈

假设任务是查询某件商品的库存，如果低于用户给定的阈值，就创建补货草稿。第一步需要确认商品标识和判断条件；第二步读取当前库存；第三步根据结果决定是否创建草稿；最后检查草稿确实存在，并把结果告诉用户。

如果库存查询失败，系统不能继续假定库存偏低。若商品标识不匹配，应重新确认对象，而不是随意选择近似商品。草稿创建超时后，也不能立即重复创建，需要先判断请求是否已经生效。这个例子虽然简单，却展示了观察如何改变行动，以及为什么工具响应的语义很重要。

## 什么时候应该停止

正常停止来自目标满足并通过相应检查。其他出口包括信息不足、用户取消、资源达到上限，以及错误无法继续处理。每种出口都应保留当前进度与未完成事项，而不是统一返回“任务完成”。模型提出结束可以作为信号，但运行程序仍要检查必要状态。

还需要识别没有进展的循环。相同查询反复返回相同错误，模型却不断改写解释，这不是真正推进。可以观察是否获得新事实、是否完成子目标、是否排除某个假设，再决定继续是否有价值。固定轮数可以兜底，但不能替代对进展的判断。

## 与计划和工作流怎样配合

ReAct 适合需要根据反馈调整步骤的部分，不要求整个应用都采用开放循环。可以先用固定流程完成身份检查与输入校验，再让一个有限循环查找资料，最后回到固定的结果整理与确认步骤。对于路径清楚的任务，直接编排工具调用可能更简单。

我的练习方式是给同一任务加入空结果、错误参数和部分成功，逐步查看系统有没有使用新观察，是否发生多余调用，以及停止理由是否真实。比较不同实现时，要保持任务、工具与完成标准一致。循环机制的价值最终体现在正确处理变化，而不是展示了多少轮动作或多少段解释。

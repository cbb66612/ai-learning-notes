# 工具接口怎样设计

## 从一个具体动作开始

我理解的工具接口，是把模型的意图变成受约束的系统动作。模型可以提出调用请求，但真正的参数校验、权限检查与执行结果应由程序决定。设计工具时，我先问“用户希望完成哪件事”，再决定需要什么接口。一个名叫“处理订单”的大工具很难让人判断它会读取、修改还是删除；拆成“查询订单”“创建退款草稿”“提交已批准退款”，动作的边界就清楚得多。

工具粒度也不能无限细。若一个简单查询必须连调许多接口，模型容易遗漏依赖，用户还要承担多轮等待。我的判断方法是：一次调用是否对应一个可解释的业务动作，失败后能否明确知道停在哪一步，返回值是否足以支持下一步决定。

## 输入需要类型，也需要业务含义

字段类型只能解决一部分错误。金额是数字，还要说明币种、单位、是否允许负数；日期是字符串，还要约定时区与格式；资源编号存在，也不代表属于当前用户。结构校验、业务校验和授权是不同的检查，不能用一个合法的 JSON 代替它们。

工具描述应写清何时使用、何时不要使用、缺少参数时如何处理。必要字段无法从请求或可信系统中获得时，应追问或返回缺失信息，不能让模型猜一个编号补齐。可选字段的默认值也要谨慎：默认“全部”可能扩大查询范围，默认“确认”可能把草稿变成真实写入。

## 输出要让下一步有依据

我会把返回结果分成成功、空结果、可恢复失败和不可继续的失败。查询没有找到数据与查询服务不可用，在用户界面上可能都没有内容，但后续动作完全不同。前者可以调整条件，后者应说明暂时不可核验。

成功输出宜包含稳定标识、必要业务字段和可定位信息。失败输出宜包含错误类别、是否可重试、需要补充什么，而不是一长段堆栈。返回内容也要控制体积：搜索工具给候选摘要，详情工具按标识打开完整内容，通常比每次都返回整库文本更容易使用。对于敏感字段，服务端应在返回前按权限过滤。

## 写操作要考虑重复与部分完成

假设一个学习用助手要创建工单。网络超时后，它无法确定请求是否已经成功；直接再提交一次，可能生成重复工单。这个例子提示我：写接口除了参数，还应设计幂等标识、结果查询和可追踪的任务编号。重试应依据错误类型，不应把所有失败都当成“再来一次就好”。

如果操作包含多个步骤，还要明确事务范围。前两步成功、第三步失败时，是回滚、补偿还是保留中间状态等待人工处理？这些规则属于业务程序，不能临时交给模型自行决定。高影响操作可以先生成可审阅的计划或草稿，再由授权者确认。

## 用一组小测试检查接口

我会给工具准备正常输入、缺少必填字段、错误单位、无权限资源、空结果、超时和重复提交等情形。检查点包括：模型是否选择正确工具，程序是否拦住无效请求，错误是否能被理解，最终回复是否忠实于返回结果。

还要测试“不该调用”的情况。例如用户只是询问退款规则，助手不应进入退款提交接口。接口质量不仅体现在调用成功率，也体现在它能否帮助系统保持清楚的动作边界。完成后再回看工具名称、描述与返回结构，删掉必须靠口头解释才能理解的歧义。
